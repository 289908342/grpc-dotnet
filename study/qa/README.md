## ⚠️ 错误模式追踪（最重要的部分）

**单题答错是知识问题，同类型的错反复出现是思维问题。** 后者更值得关注。

| # | 模式 | 出现次数 | 具体表现 | 危险程度 |
|---|---|---|---|---|
| **A** | **Happy path 假设** | 1 | 第 01 节 Q7：「只是跨进程，不太可能出现断连」 | 🔴 **最高** |
| **B** | **相邻概念混淆** | 1 | 第 02 节 Q5：把「零值不传」和「负数编码」混成一个问题 | 🟠 高 |
| **C** | **原因/优点归错来源** | 2 | 第 01 节 Q3「部署更快」；第 02 节 Q7 把「基础设施多」当性能 | 🟠 高 |
| **D** | **手段套错问题** | 1 | 第 02 节 Q5：想用「加偏移」解决零值问题（思路对，用错地方） | 🟡 中 |
| **E** | **从字面猜术语** | 1 | 第 02 节 Q6：`sint` 猜成 "string 格式的 Int"（实为 signed） | 🟡 中 |
| **F** | **术语不精确** | 3 | "库"vs"实现"、"协议"vs"格式"、"部署"vs"接入" | 🟢 低 |

### 模式 A 值得单独说

**Happy path 假设是唯一一个危险级别的模式。**

它的危害不在于"答错"，而在于**它会让你在设计中漏掉整类场景**：

```
假设"不会断连"  →  不写重连逻辑  →  断连时行为未定义
```

**自查方法**：每当你说/写"不太可能"、"一般不会"、"正常情况下"时，**停下来问一句**：

> 如果这件事发生了，我的系统会怎样？

如果答案是"不知道"，那就是个洞。

- **学完一节后**：不用回看，继续往下
