## 第一部分：阅读中的 5 个问题（主动提问）

### 阅读问题 1：protobuf 如何解决多语言问题？

**解答**：三层都保持语言中立 —— IDL（描述数据不是代码）+ wire format（只有字段号和 wire type）+ 每语言一个代码生成器。

> **跨语言一致的是「字节」，不是「API」。** 生成的代码样子不同，序列化结果完全一样。

不完全对称的地方：数值范围（Python `int` 任意精度）、命名转换、`map` 遍历顺序。

### 阅读问题 2：gRPC 可以不用 protobuf 吗？有什么成熟实践？

**解答**：可以。分两类 ——

- **换掉 wire format**：JSON / MessagePack / FlatBuffers / 自定义
- **保留 protobuf wire format，只去掉 `.proto`**：`protobuf-net.Grpc`（"code-first"，`examples/Coder`）

⚠️ 注意：protobuf-net.Grpc **不是"不用 protobuf"**，它仍用 protobuf 的 wire format，只是契约改成 C# 接口。

仓库自己的评价（`examples/README.md` L244）：
> **Code contracts can't be used by other languages** and cross-platform apps should use `.proto` contracts.

### 阅读问题 3：协议一致性会不会带来两方同时维护的负担？

**这是本轮最好的问题之一。** 解答分三层：

| 层次 | 内容 |
|---|---|
| **硬要求** | 双方必须有同一份 `.proto`。**服务名/方法名也在里面**（决定 URL） |
| **避免霰弹式维护** | NuGet 包 / Git submodule / monorepo / **`dotnet-grpc` 工具** |
| **好消息** | 兼容性规则允许**独立部署**，不需要同时升级（第 03 节） |

**`dotnet-grpc`（`src/dotnet-grpc`）的命令**：

| 命令 | 作用 |
|---|---|
| `add-file` | 引用本地 `.proto` |
| **`add-url`** | **从 URL 引用** ← 共享的关键 |
| **`refresh`** | **从源头重新拉取** ← 同步的关键 |
| `list` / `remove` | 管理引用 |

**推荐做法**：`.proto` 放独立仓库 → 两边 `dotnet-grpc add-url` → CI 加 breaking change 检测（`buf`）。

### 阅读问题 4：varint 如何保证不会有歧义？

**你已自己答对：「应该按照字节来拆分」。**

**边界由「字节」决定，不是由「位」决定。** 每个字节最高位是续位（1=继续，0=停），所以解码器逐字节读、不需要预知长度。

**补充：确实存在非规范编码** —— `1` 可以是 `01`（规范）或 `81 00`（非规范）。这解释了"同一消息可能有多种合法字节表示"→ 不能拿字节做哈希/比较。

### 阅读问题 5：gRPC 不知道 protobuf，那两端怎么保证一致？

**解答**：两端各自依赖 protobuf，各自用**同一份 `.proto`** 生成代码。

| 谁 | 负责什么 |
|---|---|
| **gRPC** | `Marshaller<T>` 抽象 + HTTP/2 传输 |
| **你** | `Marshaller<T>` 的实现 + **保证两端 `.proto` 一致** |

两个细节：
1. **`Google.Protobuf` 运行时版本不需要两端一致**，但 **`.proto` 必须一致**
2. **代码生成在各端本地构建时进行** → 共享的是 **`.proto` 源文件**，不是生成物

## Q1 varint 手算 ❌

**问题**：`message M { int32 a = 1; }`，`a = 150` 时是 `08 96 01`。
那么 `a = 1` 时是什么？`a = 300` 时呢？

**你的回答**
> a = 1 时，应该是 `08 02`？ a = 300 时，应该是 `08 12 C1`？我是这么算的，int32 是 varint，对应 Tag 就是 `08`，然后我看 150 对应 `96 01`，所以 1 应该是 02（我其实没有特别理解为啥 150 对应 9601，按我理解，转换为 HEX 应该是 96）？

**评价：❌ 两个都错了，但你的困惑指出了一个真实存在的陷阱**

| | 你的答案 | 正确 |
|---|---|---|
| `a = 1` | `08 02` | **`08 01`** |
| `a = 300` | `08 12 C1` | **`08 AC 02`** |

### 你的困惑：「150 转 HEX 应该是 96」

**你没算错 —— 150 的十六进制确实是 `0x96`。而 `varint(150)` 的第一个字节也确实是 `0x96`。**

**这不是巧合到罕见，而是 128~255 整个区间的规律**：

128~255 的二进制都是 `1xxxxxxx` —— **第 7 位本来就是 1**，而 varint 要设的续位正是第 7 位，两者重合了。

```
150 = 1001 0110
      ↑ 这一位既是"值的第 7 位"，也是"varint 的续位"
```

所以在这个区间里，**varint 的第一个字节永远等于值本身**。你从"转 HEX"的角度看，完全看不出区别。

### 正确的算法

```
v < 128:         varint = [v]
128 ≤ v < 16384: varint = [(v & 0x7F) | 0x80,  v >> 7]
```

**算 1**：`1 < 128` → `01` → 所以 `08 01`
**算 150**：`150 & 0x7F = 0x16`，`|0x80 = 0x96`，`150>>7 = 1` → `96 01`
**算 300**：`300 & 0x7F = 0x2C`，`|0x80 = 0xAC`，`300>>7 = 2` → `AC 02`

> **核心纠正：varint 不是"十进制转十六进制"，是把二进制切成 7 位一组，每组加一个续位。**

## Q2 改字段名 ⚠️

**问题**：把 `string device_id = 1;` 改成 `string deviceId = 1;`（只改名字不改号），会破坏兼容性吗？

**你的回答**
> 没问题，因为 protobuf 是按照字段来编号的，不需要了解字段名

**评价：⚠️ 对，但只对 wire format 而言**

**wire format 层面完全正确** —— 字段名不上线，改名不影响字节。

**但有三个地方会受影响**（也是官方风格指南建议"连名字也别改"的原因）：

1. **JSON transcoding** —— 开了 gRPC↔REST 转换后，字段名会出现在 JSON 里
2. **protobuf 的 JSON 映射**默认用 camelCase，改名会改变 JSON 输出
3. **工具链** —— 反射、schema registry、IDE 引用

**结论**：wire 层面安全，**但工程上仍不该改**。

## Q3 为什么是 1~15 号 ✅

**问题**：官方推荐常用字段分配 1~15 号，为什么是这个分界？

**你的回答**
> 1-15 号的话，字段向左横移三位，正好一个字节能够满足，如果再大，就要扩展一个字节来携带信息了

**评价：✅ 完全正确**

验算：

```
字段 15：(15 << 3) | 0 = 120  →  ≤ 127  →  1 字节 tag
字段 16：(16 << 3) | 0 = 128  →  > 127  →  2 字节 tag
```

**这是本轮计算类问题里答得最准的一题。**

## Q4 用编号替代字符串路径 ✅

**问题**：你们的字符串寻址如果每条消息都带完整路径，100ms 周期下带宽如何？有优化空间吗？

**你的回答**
> 实际上我们的寻址也有编号，目前编号应该是 0-100000（不一定连续，但一定不会重复），所以如果按照编号来，会不会更快一些？

**评价：✅ 方向完全正确 —— 而且你已经具备了实施它的一半**

**收益**：

| 方案 | 字节 |
|---|---|
| `"Root.Motor1.Speed"` | 1(tag) + 1(len) + 18 = **20** |
| 编号 `47213` | 1(tag) + 3(varint) = **4** |

**省 5 倍**，且解析不做字符串比较。

**但四个坑**：

| # | 坑 |
|---|---|
| 1 | **编号 0 会丢** ⚠️ —— proto3 里 0 是默认值**不传输**。若编号 0 合法，它的变化永远推不出去 → 从 1 开始编号 |
| 2 | 字节数随编号增长（0~127→1；128~16383→2；16384~100000→**3**） |
| 3 | **需要一次注册握手**（客户端要知道编号对应哪个对象）—— 额外协议设计 |
| 4 | 可读性下降（日志里 `id: 47213` 不如路径直观） |

**进阶**：对象数远小于编号上界时，可用本地映射表压成密集 ID，varint 全是 1~2 字节。

> 这正是 **OPC UA 的 NodeId / DDS 的 topic** 的思路 —— **你重新发明了工业协议里的经典优化。**

## Q5 温度 = 0.0 ⚠️

**问题**：推送"温度 = 0.0"，用 proto3 的 `double celsius = 1;` 会有什么问题？怎么避免？

**你的回答**
> 看上去是因为 proto3 里的零值不传导致的？还是说默认值是 1，这里传递的应该是 -1，就导致了负数的情况，会以一个极大值传递，占用了很多空间？如果是这样的话，默认添加一个偏移，让下限以 0 或者 1 表示，是不是就好了？

**评价：⚠️ 前半对，后半把两个问题混在一起了**

### 前半 ✅：「proto3 零值不传」—— 完全正确

**这就是 Q5 的答案。** `celsius = 0.0` 不会上线。

### 后半 ❌：混淆了两个独立问题

| 问题 | 属于 | 症状 |
|---|---|---|
| **零值不传** | **Q5** | 无法区分"值是 0"和"字段没设" |
| **负数编码膨胀** | **Q6** | `-1` 占 10 字节 |

**这是两个独立的问题，解法也不同。**

另外：「默认值是 1」❌ —— **默认值是 0**。数值类型默认 `0`，`string` 默认 `""`，`bool` 默认 `false`。

### 「加偏移」的思路 ⚠️：对，但用错地方

**思路本身是对的**，而且 protobuf 已经实现了 —— **ZigZag 就是"加偏移 + 交错"**。

但用在**零值问题**上不行：

```
偏移 +100，让 -100 变成 0
    ↓
真实值 -100 成了新的"默认值" → 依然不传输   ⚠️
```

**你只是把洞挪了个位置。** 因为 proto3 跳过的是"类型默认值"，而你永远可以让某个真实值等于默认值。

**真正的解法**：`optional`（推荐）/ `oneof` / 哨兵值。

### 深层洞察（和你们系统相关）

对**推送式变化通知**来说，「值变成 0」和「没有值」是**两个不同的事件**。用普通字段，这个信息在编码层就丢了。

应显式建模"变化事件"：

```proto
message Change {
  uint32 object_id = 1;
  oneof value {
    double numeric_value = 2;   // 明确有数值
    bool   is_invalid    = 3;   // 明确无效
  }
}
```

→ 错误模式：**B（相邻概念混淆）** + **D（手段套错问题）**

## Q6 负温度 ❌

**问题**：-20°C 用 `int32` 存占几个字节？换成什么类型更合适？

**你的回答**
> 负数一定是 10 字节，所以这部分建议是用 sint 来做（sint 是什么，string 格式的 Int 吗？）

**评价：❌ 结论对，但 `sint` 理解错了**

**字节数 ✅ 正确**：`-20` 用 `int32` 占 **10 字节**（补码高位全 1）。

**`sint` ❌ 不是 string**

> **`sint` = "signed integer"**。`s` 是 **signed**（有符号）的缩写，和 `sfixed` 的 `s` 同源。

换 `sint32` 后 `-20` 只占 **1 字节**（ZigZag: `-20 → 39`）。

**完整标量类型表**：

| proto 类型 | 编码 | 适合 |
|---|---|---|
| `int32` / `int64` | varint（补码） | **不适合负数** |
| `uint32` / `uint64` | varint | 非负 |
| **`sint32` / `sint64`** | **varint + ZigZag** | **可能为负的值** ⭐ |
| `fixed32` / `fixed64` | 固定 4/8 字节 | 大数值（> 2^28 时更省） |
| `sfixed32` / `sfixed64` | 固定 4/8 字节（有符号） | 同上 |
| `float` / `double` | I32 / I64 | 浮点 |
| `bool` | varint（0/1） | |
| `string` / `bytes` | LEN | |
| `enum` | varint | 0 必须是第一个值 |

→ 错误模式：**E（从字面猜术语）**

## Q7 重做：gRPC 为什么快 ⚠️

**问题**（重做第 01 节 Q5）：gRPC 的快主要来自哪里？哪部分是 protobuf 的功劳，哪部分是 HTTP/2 的？

**你的回答**
> gRPC 的快，一个是 protobuf 协议，极大地精简了报文，提高了传输的速率；另外一个是因为 HTTP2 协议，有非常多的基础设施，也能满足数据透传的一些需求

**评价：⚠️ 答对一半来源**

### ✅ 对的部分

「protobuf 精简了报文」—— 正确。（措辞：protobuf 是**消息格式**，不是协议。）

### ❌ 错的部分

「HTTP2 协议，有非常多的基础设施」—— **"基础设施多"不是"快"的来源，是"容易部署"的来源。**

这是第 01 节 Q3 讲的东西，和性能是**两件不同的事**。

### HTTP/2 对「快」的真实贡献

| 贡献 | 属于 |
|---|---|
| **HPACK 头部压缩**（跨请求维护表） | 省带宽 |
| **多路复用**（省掉重复的 TCP/TLS 握手） | 省延迟 |

### 完整答案（4 个来源）

| 来源 | 归谁 | 性质 |
|---|---|---|
| 报文小：不传字段名、varint、零值不传 | **protobuf** | 省带宽 |
| 解析快：按字段号跳转，不做字符串匹配 | **protobuf** | 省 CPU |
| 头部压缩（HPACK） | HTTP/2 | 省带宽 |
| 多路复用（省掉重复握手） | HTTP/2 | 省延迟 |
| ~~基础设施多~~ | — | ⚠️ **不是性能** |

→ 错误模式：**C（原因归错来源）**
