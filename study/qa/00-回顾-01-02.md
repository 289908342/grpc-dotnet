## ❌ R5：tag 结构和 varint 都没记住

**你的回答**
> 应该是 `96 08 02`？需要前面标记下 variant 类型啥的

**正确**：`08 01`

**两个错误**：
1. **顺序反了** —— 永远 `tag` 在前、`value` 在后。你把 150 的字节混进来了
2. **以为类型要"另外标记"** —— wire type **编码在 tag 里**：`tag = (字段号 << 3) | wire_type`

**「为什么不是 `08 02`」没答出**：因为 `varint(1) = 01`。**值 1 就是 1，没有变换。**

→ 已补课 + 动手练习

### R6(a) ✅ 正确 —— "零值不传输"

### R6(b) ❌ 数字错：**10 字节**，不是 5

（`int32` 负数符号扩展到 64 位，高位全 1）

**但你的顾虑很有价值** 👏
> "我比较担心，这样的话，一个 0，都会视为 10000 之类的，有些为了芝麻丢了西瓜？比如极小概率的负数，把大多数的正数的报文，都撑大了"

**这个顾虑完全正确** —— 正是"偏移方案"的真实缺陷。

**但结论应该是**：不需要自己发明偏移，**protobuf 已有 `sint32`**（ZigZag 让小正数和小负数**都**便宜）。

> **教训：先查工具是否已解决，再自己发明方案。**

### R7 ⚠️：「将无效设置为 -1」在温度场景很危险

**-1°C 是完全正常的温度**（冬天、冷库、冷冻环境）。用 `-1` 做哨兵会导致真实读数被误判。

**原则**：哨兵值要选"物理上不可能"的值。**温度没有不可能的值，所以哨兵不适用。**

正确做法：`oneof` 或独立的 `bool` 字段。

## ❌ R8：一个关键认知错误

**你的回答**
> 应该用 unary，**长连接在断连的时候，是无法重连的**，会导致发送一大堆无效信息；unary 每次都会查询状态，更安全

**「无法重连」是错的。** 这恰恰和你在 R3 说对的事情矛盾（R3 说"需要补充重连逻辑"）。

**流断了可以重建流**：

```csharp
using var call = client.WatchKernelState(request);   // 重新发起一个新的流式调用
await foreach (var change in call.ResponseStream.ReadAllAsync(ct)) { ... }
```

流式调用**不可自动重试**，所以重连逻辑要自己写 —— 但**不是不能重连**。

**漏掉的三点**：
1. **streaming 的最大风险**：消费慢会积压，**可能拖住内核**
2. **一致性**：你们**已经有一套 streaming 在跑**，新接口用另一种模式会增加维护成本
3. **streaming 的优势**：服务端压力更小（1 条流 vs 每秒 10 次调用）
