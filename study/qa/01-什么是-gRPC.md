## Q1 识别过时的 API

**问题**：看到一个教程里写 `new Channel("localhost", 5000)`，这段代码能直接用吗？如果不能，为什么？

**你的回答**
> 不能，这个是用的比较老的库，对应 Grpc.Core 相关（后续会废弃），我们现在应该用 grpc-dotnet 的实现

**评价：✅ 正确**

两处措辞需要更精确：

| 你的说法 | 更准确的说法 | 为什么重要 |
|---|---|---|
| "比较老的**库**" | **另一个实现** | 它们是平行的两个实现，不是版本新旧关系。API 完全不同，**不是升级能迁移的，是重写** |
| "后续会**废弃**" | **维护模式**（只修安全/严重 bug） | 维护模式意味着现在还能用，但别在新项目用。废弃是计划，不是已发生 |

**补充**：grpc-dotnet 里**也有** `ChannelBase`（`src/Grpc.Core.Api/ChannelBase.cs`），`GrpcChannel` 继承自它。所以 "Channel" 概念没消失，只是**构造方式**变了。

## Q2 channel 复用

**问题**：我们每秒调用 10 次，这算频繁吗？如果有人**每次调用都** `GrpcChannel.ForAddress(...)` 新建一个 channel，会发生什么？

**你的回答**
> 每秒调用 10 次应该不能算上频繁吧，要看尺度是怎么定义的。不过每次调用都去新建 channel 的做法不太合适，看上去会不断地申请资源，构造对象，这部分可能是耗时操作，导致时序有问题？

**评价：⚠️ 方向对，机制说错**

| 部分 | 判断 |
|---|---|
| "不算频繁，要看尺度怎么定义" | ✅ 直觉好 —— 取决于消息大小、并发数、单机还是集群 |
| "新建 channel 不合适，导致时序问题" | ✅ 结论对 |
| **"构造对象，这部分可能是耗时操作"** | ❌ **对象构造几乎不花钱（纳秒级）** |

**真正的原因**：连接建立的**握手链**（官方文档列出的 5 步）

```
1. Opening a socket
2. Establishing TCP connection
3. Negotiating TLS          ← 最贵
4. Starting HTTP/2 connection
5. Making the gRPC call
```

| 做法 | 一次 unary 调用耗时 |
|---|---|
| 复用 channel | **亚毫秒** |
| 每次新建 channel | **10~50 ms** |

差 1~2 个数量级。对 100ms 周期来说，直接表现为**周期拉长、抖动剧增**。

**漏掉的第二点：泄漏** —— `GrpcChannel` 是 `IDisposable`，不 dispose 的话底层连接要等 GC 才回收，高频新建会迅速耗尽 socket。

→ 错误模式：**C（原因归错来源）**

## Q3 gRPC vs REST

**问题**：gRPC 是 REST 的替代品吗？我们现有的 REST 接口应该全部换成 gRPC 吗？

**你的回答**
> gRPC 和 REST 应该各有千秋，不能说谁是谁的替代品，不同的情况下，他们各有优劣吧。不过 gRPC 好处是，复用了 HTTP2 这个基础设施，本质上只是一个标准化协议，可能部署起来更快？

**评价：⚠️ 一个点很准，一处要修正**

| 部分 | 判断 |
|---|---|
| "各有千秋，不能说谁替代谁" | ✅ 正确 |
| **"复用了 HTTP/2 这个基础设施"** | ✅ **抓得很准，这正是核心** |
| "本质上只是一个标准化协议" | ⚠️ 措辞：gRPC 不是"一个协议"，是**一套规范 + 代码生成工具 + 运行时库**，借用了 HTTP/2 作传输 |
| **"可能部署起来更快"** | ❌ **要修正** |

**"部署更快"的两面**：

| | |
|---|---|
| ✅ **接入现有运维体系更快** | 防火墙、监控、代理都认 HTTP |
| ❌ **端到端打通可能是额外工作** | 需要 HTTP/2 端到端（中间有 HTTP/1.1 代理就挂）；默认要求 TLS；**L4 负载均衡对 gRPC 基本无效**（所有调用挤一条连接，全打到一个后端） |

→ 错误模式：**C（优点归错来源）** + **F（术语不精确）**

## Q4 什么情况下不该用 gRPC

**问题**：什么情况下**不该**用 gRPC？举一个你们系统里可能遇到的例子。

**你的回答**
> gRPC 不能作为银弹使用，比如不需要跨进程、跨设备的通讯，或者说，高实时性的通讯，因为 gRPC 会有断连的风险，本身不够稳定

**评价：⚠️ 结论对，理由危险**

| 部分 | 判断 |
|---|---|
| "不需要跨进程/跨设备就不用" | ✅ 正确。同进程内直接调函数，无需序列化 |
| "高实时性不适合" | ✅ 结论正确 |
| **"gRPC 会有断连的风险，本身不够稳定"** | ❌ **这个理由会把你带偏** |

**为什么危险**：

任何走 TCP 的协议都会断连，这不是 gRPC 特有的。真正的原因是：

> **gRPC 给不出延迟上界。** GC 暂停、TCP 重传、线程调度，都可能让一次调用从亚毫秒变成几百毫秒。

**说"不稳定"会让你想到"加重试"—— 但重试解决不了延迟问题，只会让延迟更长。**

**正确的框架**：

| 适合 | 不适合 |
|---|---|
| **软实时**：监控、HMI、配置下发 | **硬实时**：控制环、安全联锁 |

**漏掉的场景**：浏览器直连、需要 `curl` 调试、需要 HTTP 缓存语义、超大数据块。

→ 错误模式：**C（诊断归错来源，导致错误对策）**

**你的回答**

## Q6 keepalive 为什么做不到 ⭐

**问题**：grpc-dotnet 不支持 keepalive。**为什么**？这个限制是 gRPC 设计上的疏忽，还是一种必然的取舍？

**你的回答**
> 应该是必然的取舍，因为连接这部分是 HTTP2 协议来实现的，gRPC 本质上只是一个标准化的消息格式。如果需要 keepalive，需要外部自行提供一个心跳相关的机制

**评价：✅ 最佳答案**

方向完全正确。三处可以升级：

**① 责任方更精确**

不是"HTTP/2 协议"，而是 **.NET 的 HTTP/2 实现**（`SocketsHttpHandler` / Kestrel）。责任方是**平台实现**，不是协议。

**② 一个关键升级**

**HTTP/2 规范里其实有 PING 帧**，协议层是有保活能力的。所以问题不在协议，在**实现没暴露给 gRPC**。这是平台层限制，理论上能被 .NET 修掉。

**③ 结论对，而且比仓库文档更准**

`doc/implementation_comparison.md` 说 keepalive "not supported"，但**那是 .NET Core 3.x 时代的说法**。.NET 5+ 已经支持：

```csharp
var handler = new SocketsHttpHandler
{
    KeepAlivePingDelay = TimeSpan.FromSeconds(60),
    KeepAlivePingTimeout = TimeSpan.FromSeconds(30),
};
var channel = GrpcChannel.ForAddress("https://localhost:5001", new GrpcChannelOptions
{
    HttpHandler = handler
});
```

**但有一个硬前提**（官方文档 Important）：服务端不支持 PING 时，客户端单方面开启**反而会被 GOAWAY 踢掉连接**。

→ 详见 [`../pitfalls.md`](../pitfalls.md) 坑 1

## Q7 该选 unary 还是 server streaming

**问题**：如果你们要新做一个"应用读取内核状态"的接口，你会选 unary 还是 server streaming？说出理由，以及不确定的地方。

**你的回答**
> 我觉得应该是 server streaming，因为应用和内核应该是持续连接的。用 unary 的好处是一次断连不影响后续的状态，但我觉得，应用和内核应该只是跨进程，不太可能出现断连的情况。unary 每次都需要重新建立通讯，性能上可能会有一定的损耗？

**评价：⚠️ 结论可能对，但有两个错误前提，且漏了最大风险**

### 最佳直觉 ✅（你自己说出来了，但没意识到分量）

> **"用 unary 的好处是一次断连不影响后续的状态"**

这正是**错误隔离**：

| | 断连后果 |
|---|---|
| Unary | 一次失败只影响这一次，**且可重试** |
| Streaming | 一条流断了，**断连期间所有数据全丢**，且**不可重试** |

对 10Hz 推送：streaming 断一次 = 丢掉这段时间的**所有**内核变化；unary 最多丢一次。

### 错误前提 1 ⚠️：「只是跨进程，不太可能出现断连」

**这是本次讨论最危险的一句。**

会断的情况：内核重启（升级、崩溃恢复）、应用重启、安全软件干预、UDS/named pipe 对端进程退出。

**更重要的**：「不太可能」≠「不会」。**假设不断连 = 断连时行为未定义。**

**而且这和你在 Q4 说的"gRPC 会有断连的风险"直接矛盾。** 同一个系统，两个相反的前提 —— 说明其中一个是从直觉推出来的，不是从故障场景推出来的。

→ 错误模式：**A（Happy path 假设）** 🔴

### 错误前提 2 ⚠️：「unary 每次都需要重新建立通讯」

**不对。** Unary **不复用 HTTP/2 stream，但复用 TCP 连接**。

`GrpcChannel` 内部有连接池，每次 unary 只是在**已有连接上开一条新 stream**（发一个 HEADERS 帧）。

> Unary 和 streaming 的差别是 **stream 的生命周期**，不是 **TCP 连接**。

（这正是 Q2 的知识点 —— 你漏掉的机制在这里又出现了一次。）

### 漏掉的最大风险 ⚠️：流控积压可能拖住内核

```
应用消费慢（UI 卡顿 / GC）
    → HTTP/2 流控窗口耗尽
        → 服务端（内核侧）写入阻塞   ⚠️
```

**工控系统里这可能是不可接受的：应用端 UI 卡顿不应该影响内核实时性。**

### 还有两个设计约束

1. **Server streaming 的客户端只能用「取消」停止流**（没有请求流）。如果取消开销影响服务端，官方建议改用双向流。
2. **流式调用必须 dispose** —— 否则**服务端会一直留着这条流**。

### 结论修正

| 你的理由 | 修正 |
|---|---|
| "应用和内核持续连接" | ❌ unary 也是持续连接 |
| "unary 每次重新建立通讯" | ❌ 只是新建 stream |
| ✅ **真正该用的理由** | 变化是**事件驱动**的，不知道下次何时来 |
| ⚠️ **必须评估** | 流控积压会不会拖住内核 |

**另外你没提**：你们**已经有一套 100ms 推送在跑**了。新接口为什么和已有的不一样？一致性本身有价值。
