## 1. 这是什么

**Protocol Buffers（简称 protobuf）是一种把结构化数据变成字节的格式，外加一套配套工具。**

它解决第 01 节那张清单里的第 1、2、7、9 项：**编码、序列化、版本兼容、多语言**。

用起来分三步：

```
1. 你写 .proto      ← 描述"数据长什么样"
2. 工具生成代码      ← 每种语言一份
3. 运行时读写字节    ← 你不用管
```

> **重要澄清**：protobuf **不是 gRPC 的一部分**。
> 它们是两个独立项目，只是默认搭配使用。第 3 节会看到 gRPC 在哪里"接上"protobuf —— 那个接缝可以换掉。

## 2. 为什么要这样设计

### 设计时面临的两个约束

| 约束 | 为什么难 |
|---|---|
| **消息要尽可能小** | 网络传输成本 |
| **协议要能演进** | 加字段**不能**让老程序崩 |

JSON 的答案是"字段名 + 文本"—— 可读性换来了体积。protobuf 的答案是两招：

> **用数字代替名字，用变长编码代替固定宽度。**

### 核心机制 1：字段号 —— 不传字段名

```proto
message Reading {
  string device_id = 1;   // ← 这个 1 是"字段号"，不是默认值！
  double celsius  = 2;
}
```

⚠️ **常见误解**：很多人以为 `= 1` 是默认值。**不是，它是这个字段的永久身份编号。**

线上传输的是 `1`、`2` 这些数字，**不是** `"device_id"`、`"celsius"`。
字段名只存在于你本地生成的那份代码里。

### 核心机制 2：varint —— 小数字占更少字节

每个字节的结构：

```
┌─ 最高位：续位（1 = 后面还有字节）
│┌──────┐
1 0010110
```

- 最高位 = 1 → 后面还有字节
- 最高位 = 0 → 这是最后一个字节
- 剩下 7 位才是数据

| 数值范围 | 占用 |
|---|---|
| 0 ~ 127 | **1 字节** |
| 128 ~ 16383 | 2 字节 |
| … | … |
| 最大 64 位整数 | 10 字节 |

**例子：`150` → `96 01`**

```
10010110 00000001    原始
 0010110  0000001    去掉续位
 0000001  0010110    转成大端序
   00000010010110    拼接
 128 + 16 + 4 + 2 = 150
```

> **记住：数字越小越便宜。** 后面（字段号分配、负数问题）都要用到这一点。

### 核心机制 3：wire type —— 怎么知道下一个字段是什么类型

每条记录结构是 `tag + value`：

```
tag = (字段号 << 3) | wire_type
              ↑
        低 3 位是类型
```

| ID | 名称 | 用于 |
|---|---|---|
| 0 | VARINT | int32 / int64 / uint32 / uint64 / sint32 / sint64 / bool / enum |
| 1 | I64 | fixed64 / sfixed64 / **double** |
| 2 | LEN | **string** / bytes / 嵌套 message / 打包的 repeated |
| 5 | I32 | fixed32 / sfixed32 / **float** |

**这是整个设计的精髓** —— 因为 wire type，接收方遇到**不认识的字段**时，能算出该跳过几个字节。

> 这就是第 03 节「版本兼容」的技术基础：**老程序能安全跳过它不认识的新字段。**

### 完整走一遍：150 是怎么变成 `08 96 01` 的

```proto
message Test1 {
  int32 a = 1;
}
```

设 `a = 150`，序列化后 3 个字节：

```
08 96 01
```

**`08` 是 tag：**
```
08 = 0000 1000
     └──┘ └┴┴─ wire type = 0 (VARINT)
     字段号 = 1（右移 3 位）
```

**`96 01` 是 varint 编码的 150。**

整条记录 = `字段1, 类型VARINT, 值150`。**完全看不到字段名 `a`。**

## 3. 现在是怎么实现的

### protobuf 的代码不在这个仓库里

| 部分 | 在哪 |
|---|---|
| 运行时库 `Google.Protobuf` | 独立 NuGet 包，**不在本仓库** |
| 代码生成器 `Grpc.Tools` | 在 `grpc/grpc` 仓库，**不在本仓库** |
| **接入点 `Marshaller<T>`** | `src/Grpc.Core.Api/Marshaller.cs` ← **本仓库** |

### 关键设计：gRPC 根本不知道 protobuf 的存在

`Marshaller<T>` 的全部内容就是两个委托：

```csharp
public class Marshaller<T>
{
    readonly Func<T, byte[]> serializer;
    readonly Func<byte[], T> deserializer;
    // ...
}
```

**gRPC 只管调这两个函数，不关心里面是 protobuf、JSON 还是别的什么。**

这解释了两件事：

1. 为什么 protobuf 的代码不在这个仓库 —— gRPC 不需要知道
2. 为什么 `examples/Coder` 能把序列化换成 protobuf-net —— 换掉 `Marshaller` 就行

> **这是"面向接口解耦"的教科书级例子，而且就在一个你每天用的库里面。**

### 生成的代码大概长什么样

```csharp
// .proto 里的每个 message → 一个类（示意）
public sealed partial class Reading : IMessage<Reading>
{
    public string DeviceId { get; set; } = "";
    public double Celsius  { get; set; }
    // 内部有序列化/反序列化逻辑，你不用写
}
```

## 4. 优点

最直观的方式是**算一笔账**。同一条消息：

```proto
message Reading {
  string device_id = 1;   // "PLC-01"
  double celsius   = 2;   // 23.5
  int32  status    = 3;   // 0
}
```

### JSON 版本

```json
{"deviceId":"PLC-01","celsius":23.5,"status":0}
```

**47 字节**。其中**字段名占 27 字节**：

| 内容 | 字节 |
|---|---|
| `"deviceId"` | 10 |
| `"celsius"` | 9 |
| `"status"` | 8 |
| **字段名合计** | **27（占 57%）** |

### protobuf 版本

| 字段 | 字节数 | 构成 |
|---|---|---|
| `device_id` | 8 | tag `0A` + 长度 `06` + `PLC-01`(6) |
| `celsius` | 9 | tag `11` + IEEE754 double(8) |
| `status` | **0** | 值是 0，**proto3 不传输默认值** |
| **合计** | **17 字节** | |

**17 字节 vs 47 字节 —— 小 64%。**

> 手算值，字节级误差可能有。想实测可用 [protoscope](https://github.com/protocolbuffers/protoscope) 把字节 dump 成可读形式。

### 归纳：protobuf 到底省在哪

| # | 来源 | 本例贡献 |
|---|---|---|
| 1 | **不传字段名** | 省 27 字节 ← **主要来源** |
| 2 | **varint** | 小整数只占 1 字节 |
| 3 | **零值不传** | `status` 省了 2 字节 |
| 4 | **解析快** | 按字段号直接跳转，**不做字符串匹配** |

**这四条全是 protobuf 的功劳，不是 HTTP/2 的。** —— 这是第 01 节 Q5 答案的一半。

## 5. 缺点 / 代价

| # | 代价 | 说明 |
|---|---|---|
| 1 | **不可读** | 人眼看不了，必须用工具。调试比 JSON 麻烦 |
| 2 | **负数用 `int32` 膨胀到 10 字节** ⚠️ | 见下，**对工控场景特别相关** |
| 3 | **零值不传** ⚠️ | 优点也是坑：**无法区分"没设置"和"设为 0"** |
| 4 | **改 `.proto` 有严格规则** | 第 03 节专门讲 |
| 5 | **序列化顺序不保证** | 不能靠字节比较判断两个消息相等，也不能直接做哈希 / CRC |
| 6 | **2 GiB 上限** | 超过会拒绝序列化 |

### 缺点 2 详解：负数的坑 ⚠️

`int32` 用**二进制补码**编码负数，最高位是 1 → **必须用满 10 字节**。

| 写法 | 值 | 占用 |
|---|---|---|
| `int32` | `1` | 1 字节 |
| `int32` | `-1` | **10 字节** ⚠️ |

**而工控场景里负数很常见**：负温度、位置偏移、压差、反向速度……

解决办法：用 **`sint32` / `sint64`**（ZigZag 编码）：

| 原值 | 编码后 |
|---|---|
| 0 | 0 |
| -1 | 1 |
| 1 | 2 |
| -2 | 3 |

**负数和小正数都只占 1 字节。**

> **规则：只要这个字段可能出现负数，就用 `sint*` 而不是 `int*`。**

### 缺点 3 详解：零值不传的坑 ⚠️

proto3 里 `status = 0` **不上线**，接收方拿到默认值 0。

**你无法区分这两种情况：**

```
对方明确设了 status = 0      ← 有意图
对方根本没设 status 这个字段   ← 没意图
```

**工控场景的风险**：如果 `0` 有业务含义（"停机"、"无故障"、"原位"），这个歧义会变成 bug。

三种解法：

1. 用 `optional`（proto3 后来加回了字段存在性支持）
2. 用一个不可能的哨兵值
3. **把 0 定义成明确的枚举成员**，而不是用数字 0 表示"无"
